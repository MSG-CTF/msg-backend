# Windows 팀별 대기열

Windows 원격 실행에만 적용한다 일반 문제의 컨테이너 생성과 채점 방식은 바뀌지 않는다

- 총 실행 횟수에는 제한이 없으며 팀당 대기 또는 실행 요청은 한 건만 접수한다
- 같은 요청 키와 같은 파일을 다시 보내면 기존 접수 결과를 반환한다 다른 요청 키로 중복 접수하면 기존 팀 슬롯을 유지한다
- Runtime은 준비된 파일을 접수 순서대로 VM에 배정한다 여러 워커가 동시에 처리해도 뒤의 준비된 요청이 앞선 요청을 추월하지 않는다
- 파일을 아직 가져오지 못한 요청 때문에 다른 팀의 준비된 파일까지 막지는 않는다 순서는 준비 상태에 따라 바뀔 수 있다
- 앞선 요청이 VM에 배정되면 다음 팀은 다른 READY VM을 받을 수 있다 실행 완료와 VM 정리 완료는 별도로 처리한다
- 실행 완료가 확인된 팀이 다시 요청하면 기존 대기 팀 뒤에서 차례를 받는다 실행 여부 불명 상태는 기존 요청을 확인할 때까지 새 요청을 막는다

참가자 화면과 관리자 실행 기록은 보이는 동안 5초 간격으로 갱신한다 Backend는 팀의 개별 조회를 최대 5초에 한 번 Runtime에 전달하며 작업 워커도 마지막 조회 시각 순으로 갱신한다 확인한 지 15초가 지난 순번은 현재 순번으로 표시하지 않는다

Runtime의 체커 응답에는 선택 필드 queue_state와 queue_position이 추가된다 상태는 QUEUED, PREPARING, RUNNING 중 하나이며 팀 ID와 다른 팀의 파일 정보는 노출하지 않는다 Backend의 응답은 queue_policy, queue_position, queue_observed_at으로 현재 팀의 대기 상태를 전달한다 순번은 실행 시각을 보장하지 않는다

DB 스키마 변경은 없다 대기 요청은 기존 PostgreSQL 실행 기록에 보관하며 워커 재시작 뒤에도 같은 접수 순서를 사용한다 Runtime을 먼저 적용하고 Backend, Frontend 순으로 반영한다 구버전 Runtime은 기존 실행 준비 표시로 호환된다
