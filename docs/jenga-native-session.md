# Jenga 일반 세션과 플랫폼 토큰 검증

현재 출제자 구현은 jenga_session 쿠키에 경기 식별자·generation·marker와 임의의 서버 세션 식별자를 저장한다
팀 토큰은 Jenga의 영속 SQLite에 암호화해 보관하고 보호된 요청마다 플랫폼의 현재 판정을 확인한다
검토한 출제자 변경은 [Jenga 세션 폐기 수정](https://github.com/MSG-CTF/2026_MSG_CTF/pull/139)이며 고정 소스는 회귀 검증의 upstream.json에 기록한다

플랫폼의 토큰 검증 API는 문제별 내부 자격, 현재 서명 키 버전, 문제별 토큰 행과 팀 정지 상태를 확인한다
유효하지 않은 토큰에 valid=false를 반환하면 Jenga가 서버 세션과 브라우저 쿠키를 폐기한다
팀 정지 해제나 토큰 행 복구 뒤에도 폐기한 쿠키는 다시 허용하지 않으며 새 로그인이 필요하다
플랫폼의 HTTP 오류나 키 권한 장애는 Jenga에서 502로 차단하고 정상 세션은 복구 후 재시도할 수 있다
경기 namespace·generation과 세션 키 퇴역의 판정은 원본 서버 세션 저장소가 담당한다

이전 초안의 session 쿠키 전용 앞단 API와 Caddy 삽입 코드는 최신 정상 쿠키를 차단하므로 반영 대상에서 제거했다
현재 원본의 보호된 요청은 자체 검증 경로를 사용하며 플랫폼에서 쿠키를 재해석하거나 별도 캐시 기록에 연결하지 않는다

## 재현과 CI

tools/jenga_contract/contract_suite.py는 원본 Jenga와 실제 Django 플랫폼을 각각 로컬 HTTP 서버로 실행한다
플랫폼 저장소에는 테스트용 PostgreSQL과 Redis를 사용하고 원본 게임은 임시 SQLite를 사용한다
정상 응답을 만드는 가짜 플랫폼이나 네트워크 요청 대체 함수는 사용하지 않는다
출제자 파일 세 개의 SHA-256이 검토 기록과 다르거나 원본 소스가 없으면 검증이 실패한다

검증 항목은 정상 로그인·쿠키 갱신 금지·팀 정지·토큰 회수 및 복구·다른 팀과 문제의 분리·변경 요청 차단·플랫폼 장애 복구·서버 재시작·경기 세대 변경·키 epoch 교체·기존 형식 쿠키와 변조된 서버 세션 거절이다
차단된 변경 요청과 키 epoch 교체에서는 게임 테이블의 행도 비교한다
일반 백엔드 테스트와 별도인 jenga-contract-tests 작업에서 실행하고 해당 작업이 성공해야 main 자동 배포가 진행된다
Flask와 그 의존성은 전용 테스트 requirements에만 설치한다
비공개 출제자 소스는 기존 RELEASE_POLL_GITHUB_TOKEN으로 고정 커밋을 읽고 checkout 뒤에는 Git 자격을 남기지 않는다

이 검증은 고정된 양쪽 구현 사이의 HTTP 계약 증거이며 실제 참가자의 접속·토큰·게임 상태를 변경하지 않는다
새 출제자 버전을 연결할 때는 소스 고정값과 파일 해시를 함께 검토하고 같은 회귀 검증을 다시 실행한다
